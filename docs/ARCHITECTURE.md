# Архитектура

## Решение и текущий объём

Pipeline v3 реализует гибридный цикл структурированных гипотез Qwen и численного поиска.
Qwen выбирает изменение по измеренным ошибкам; harness проверяет рецепт,
материализует код, допускает обучение по ресурсам, независимо оценивает результат
и сохраняет CSV. Численные trials выполняет Optuna. Статус проверок и ограничений —
этап 10 `PLAN.md` и `REFACTOR_RESULT.md`; прежние PIPELINE/NIGHTLY результаты сохраняют историю.

## Направление зависимостей

```text
entrypoints → adapters → application → domain
     └───────────────→ application / domain
```

Стрелки обозначают импорты. При выполнении application вызывает адаптеры через определённые в application интерфейсы. Domain не импортирует остальные слои. Application не импортирует конкретные адаптеры. Entry points создают реальные реализации и передают их в сценарии через конструкторы/аргументы; глобального service locator нет.

Domain и application используют стандартную библиотеку и dataclass/Enum/Protocol. Pydantic проверяет внешние сообщения на стороне адаптеров; pandas/sklearn и модели живут в ML/data-адаптерах. Контракты импортов закреплены в `pyproject.toml`.

## Модули и интерфейсы

| Модуль | Ответственность и предполагаемый интерфейс |
|---|---|
| domain | TaskSpec, ValidationProtocol, Hypothesis, Experiment, Score, ErrorReport, RunBudget. Допустимые переходы статусов, сопоставимость результатов и правила отбора. |
| application/use_cases | Подготовить задачу, выполнить эксперимент, провести исследование, завершить запуск. Координация через порты, без SDK, файловых форматов и subprocess. |
| application/ports | LanguageModel, TaskData, ExperimentRunner, ExperimentStore, Evaluator, SubmissionWriter, Clock. Только интерфейсы, необходимые реальным сценариям и их тестовым реализациям. |
| adapters/llm | OpenAI-compatible Qwen, tool schemas, проверка аргументов, usage, ограниченные retries, перевод SDK-ответов в типы application. |
| adapters/data | Чтение task.md, CSV и словаря, профиль данных, материализация train/validation для worker. |
| adapters/execution | Запуск worker/candidate, логи на диске, deadline, завершение дерева процессов, контроль CPU/RAM. |
| adapters/ml | Starter-кандидаты, fit/predict, метрики и диагностика. На внешнем интерфейсе — пути/идентификаторы артефактов, внутри — dataframe/ndarray и библиотечные модели. |
| adapters/storage | JSONL-журнал, версии кода, атомарные записи, восстановление и поиск результатов. Числа пишет harness, комментарии LLM помечены отдельно. |
| entrypoints | Аргументы CLI, окружение, пути, сборка зависимостей, exit codes. |

Не заводим репозиторий и отдельный use case для каждого dataclass. Порт появляется там, где нужны реальный и тестовый способы исполнения или несколько ML-реализаций.

## Контракты

**Запуск:** `python solution.py /path/to/task.md`, без аргумента — `task.md`. `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_MODEL` передаются окружением. По умолчанию backend=portfolio (CatBoost/LightGBM), search-mode=qwen. Доступны search-mode=optuna/none; --baseline-only совместим с none. Явный backend сохраняет одиночный запуск. Относительные пути данных разрешаются от каталога task.md. Формат и путь submission извлекаются из задачи и образца; два публичных target не зашиваются в код. MCP из исходного baseline не является внешним контрактом и для нашей оболочки не требуется.

**TaskSpec:** target, ID, тип задачи, метрика/направление, labels или probabilities, порядок классов, схема submission и признаки времени/групп. Распознанное LLM описание сверяется с файлами. При противоречии запускается ограниченное уточнение, а не молчаливое обучение с догадкой.

**Кандидат:** версионированный Python-код и параметры; адаптер создаёт обучаемый объект с fit/predict и при необходимости predict_proba. Worker обучает его на предоставленном разбиении и возвращает артефакты. Обучаемые преобразования fit-ятся только на обучающей части. Метрика из stdout не является результатом эксперимента.

**Эксперимент:** ID/parent, гипотеза, хеш кода/параметров/данных, validation protocol ID, уровень проверки (smoke/full), статус, score, диагностика, время, пути артефактов. Результаты с разными протоколами не ранжируются вместе. Смена разбиения требует переоценки сравниваемых кандидатов.

**Ошибка модели:** измеренные ошибки по классам или достаточно большим сегментам, изменения против родителя. Наблюдаемая связь не объявляется доказанной причинностью. Неудачи сохраняются вместе с контекстом проверки.

**Предложения:** tool исполнения — `propose_experiment`, `column_details` читает профиль
до трёх раз по 1–8 названным признакам за гипотезу.
`Proposal` и `ResolvedExperiment` находятся в domain; внешняя Pydantic-схема —
в adapters/llm. Явно задаются parent, task kind, backend, целевая ошибка либо
exploratory-гипотеза, rationale, expected effect, параметры и преобразования.
Разрешены CatBoost/LightGBM и небольшой allowlist параметров с диапазонами;
training objective выбирает проверенный backend по task kind. Произвольные
kwargs, eval_metric, seed, потоки, пути и изменение split не принимаются.

**Признаки:** штатные операции — drop, signed_log1p, train-frequency encoding.
Для нового преобразования Qwen может вернуть Python с `build_transformer()`:
объект реализует `fit(X)` и `transform(X)`. В fit передаются только train features,
без y; результат должен сохранить index/порядок строк и единую схему колонок.
Преобразование обучается заново на разрешённом train каждого worker и frozen refit.
Код исполняется внутри существующего worker с deadline/RSS limits; это не
песочница для враждебного Python. Model factory формирует harness.

**Численный поиск:** `PipelineRecipe` сохраняет совместимое представление
`ResolvedExperiment`. Один каталог диапазонов backend используется в валидации,
описании Qwen и Optuna. Каждый trial создаёт новый полный pipeline, fit преобразований
видит только inner-train; group/time split строится до преобразования признаков.
Inner early stopping сохраняет число итераций для frozen refit. Совместимость study
включает данные, индексы split, схему, код преобразования, параметры, метрику и seed.
Потомок наследует исполненные параметры и признаки; переданные параметры заменяют
одноимённые, непустой список преобразований/исходник заменяет родительский.
Смена backend сохраняет признаки и сбрасывает модельные параметры.

**Учёт LLM:** перед каждым запросом заново рассчитываются оставшиеся секунды,
токены и резерв финализации. Reported usage и консервативный charge неизвестных
попыток различаются; прерванная сессия с неучтённым usage запрещает новые запросы.
Pipeline marker v3 отклоняет старые исследовательские журналы до их изменения.
Baseline-only память без LLM-сессий совместима. Старый ReAct use case остаётся
для legacy/scripted проверок, но CLI Qwen его не использует.

## Исследовательский цикл

1. Проверить задачу и фиксированную валидацию; получить baseline и ранний CSV.
2. Передать Qwen компактные измеренные ошибки, fitted parent recipe, названия признаков,
   прошлые результаты и свежий бюджет. Получить одно структурированное предложение.
3. Проверить схему/allowlist/совместимость, отклонить no-op и повтор рецепта.
   Сохранить requested proposal, resolved spec и effective code с SHA-256.
   При коррекции передаются точный отвергнутый рецепт и отказ последней попытки.
4. Выполнить smoke; сравнить стоимость полного обучения с min(worker timeout,
   remaining search time). Оценка: 1.5 × max(smoke × row-ratio^0.65,
   same-backend baseline × tree-complexity × tuning-factor). Это эвристика с
   зафиксированными допущениями, не гарантия; полный worker ограничен deadline.
   Автоматического скрытого уменьшения параметров нет. Отказ содержит числа.
5. Независимый evaluator считает full score и paired error delta; журнал атомарно
   сохраняет результат, parent delta, прогноз/реальные затраты и provenance.
   `executed_recipe` отдельно фиксирует выбранные Optuna параметры и отключённый
   поиск для frozen refit; именно он становится parent recipe следующей гипотезы.
   Verifier сверяет этот рецепт и его hash с фактическим result.json worker.
6. Следующая гипотеза получает факты предыдущей. Максимум 12 гипотез по оставшемуся бюджету, каждая
   с максимум 2 коррекциями; успешное full заканчивает гипотезу немедленно.
7. После каждого содержательного шага выполнять локальную настройку лучшего
   полного pipeline. После трёх гипотез без улучшения, отказа API или неизвестного
   usage продолжать только локально. В контрольных точках публиковать улучшенный
   CSV без control и замораживания поиска, если refit помещается в search budget.
8. Заморозить финалистов и веса 25/75, 50/50 или 75/25 на development, выполнить
   control как аудит и frozen refit, сохранить CSV. Control не меняет ranking. Итоговое
   LLM-объяснение в первой версии отключено: ни одного запроса ради review,
   текст не является условием успеха и не изменяет измеренные факты.

Новый functional gate v3 проверяет обе исходные публичные задачи, seed 42,
единую конфигурацию/исходники и реальные proposal→recipe→code→full артефакты.
CSV независимо сравнивается с frozen refit. Непустой текст и старый gate_passed
не принимаются как доказательство. Улучшение score проверяется отдельной матрицей.

## Отказы и ресурсы

- Один тяжёлый процесс обучения за раз. Ограничиваем число потоков и учитываем дочерние процессы.
- Контекстное окно, число API-попыток, расход токенов и wall-clock учитываются отдельно. Цена и лимиты токенов требуют подтверждения у провайдера; из 600 ₽ нельзя вывести точное число вызовов без тарифов.
- Обучение не сопровождается опросами LLM. Его результат ждёт код harness; stdout/stderr пишутся в файл, в контекст возвращается ограниченная сводка.
- Таймаут/падение/API-ошибка не уничтожают ранее сохранённый submission. Запись — во временный файл с проверкой, затем atomic replace на том же filesystem.
- Поиск останавливается с резервом на проверку, refit, predict и запись, рассчитанным по измеренному времени успешных запусков. Неудачные worker расходуют абсолютный deadline, но не повышают прогноз стоимости финалистов; ранний fallback учитывается как refit.
- Отдельный процесс/evaluator не является security sandbox. Права и доступность OS-изоляции проверяем в Linux-контейнере; не обещаем защиту holdout только разнесением файлов.

## Зависимости и границы первой реализации

Основной стек: stdlib, openai/httpx/pydantic/tenacity, pandas/numpy/scipy/sklearn, CatBoost/LightGBM/XGBoost/Optuna, psutil/joblib/cloudpickle. AutoGluon 1.3.1 — extra `automl`, самостоятельный кандидат и сравнительный ориентир. Используем явный набор разрешённых моделей без предобученных весов и скачиваний.

Версии организаторов сохранены в `task/reference/requirements.txt`; это каталог доступного ПО, а не требование импортировать всё. LangChain/LangGraph, MCP и второй агент текущему циклу не нужны. Dev-зависимости отделены от runtime.

Первая реализация покрывает табличную регрессию, binary/multiclass и распространённые метрики. Возможности private шире публичного описания не подтверждены. Смена задачи не требует изменений исходников; реальные пределы покрытия измеряются на дополнительных локальных кейсах.


## Итог v3 и представление

`application/use_cases/hybrid_search.py` управляет чередованием исследований,
стагнацией и переходом на локальную работу. Entry point собирает зависимости,
готовит контекст и вызывает policy; ResearchWorkspace исполняет общий рецепт,
проверяет артефакты и сохраняет измерения. Runner/evaluator и атомарная запись сохранены.

`run-result.json` версии 3 содержит отдельные `result_status`/`search_status`,
выбранный рецепт/источник, score/protocol, stop reason, отказы, ресурсы и usage.
CLI сохраняет этот итог; verifier сверяет с независимыми refit-артефактами;
панель читает те же факты с совместимым просмотром старых запусков. Resume v2
отклоняется до изменения исследовательской памяти.

Профиль хранит словарь, типы, пропуски, уникальность, квантили/частые категории,
target только train и различия train/test. Диагностика охватывает все признаки;
финальное сообщение ограничено после добавления рецепта и измерений. Приоритет —
метрика, свежий бюджет, рецепт родителя и выбранные измеренные свидетельства.
Классификационные артефакты всегда содержат вероятности с явным порядком классов;
label submission получается после согласования классов и усреднения вероятностей.
