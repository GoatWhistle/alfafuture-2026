## Что известно о 503

Пять сохранённых ошибок имеют HTTP 503, `service_unavailable_error`, `capacity_unavailable` и время ответа 60.65–60.82 s. Все пять возникли при единственном принудительно выбранном инструменте. Есть и успешные запросы с таким выбором; размер контекста сам по себе причину не объясняет.

**Перегрузка провайдера не установлена.** Нужно различить поведение `tool_choice`, внутренний таймаут/маршрутизацию endpoint и влияние запроса. Не менять транспорт по одной догадке.

Последняя A/B-диагностика была прервана: сохранён только первый ответ. При принудительном `edit_file` и единственной схеме `edit_file` сервер за 9.749 s вернул HTTP 200 с вызовом `inspect_data`. Это нарушение ожидаемого контракта выбора инструмента; оно ещё не доказывает причину 503. HTTP 200 сам по себе не означает пригодный ответ агента.

## Последовательность работы

### 1. Воспроизвести и локализовать поведение API

Использовать сохранённый неуспешный payload, менять один фактор за раз. Для начала — одинаковые messages/tools/max_tokens с forced tool_choice и без него, чередуя порядок. SDK retries выключить, запросы выполнять последовательно. Сохранять HTTP status, время, finish_reason, имена/валидность tool calls, reported usage и параметры опыта без секретов.

Затем, только если необходимо для различения гипотез, сравнить короткий payload с исходным или прямой SDK-вызов с адаптером. Каждый результат должен указывать, какую гипотезу он подтверждает или опровергает. Успех forced-edit probe не считать успехом harness.

Критерий этапа: воспроизводимый симптом и минимальный эксперимент, различающий причины, либо точно обозначенное внешнее ограничение с сохранёнными доказательствами. Не запускать полный ML-портфель ради каждого API probe.

Диагностический раунд — максимум 12 HTTP-попыток, без параллельных запросов. Если исходный и минимальный запросы устойчиво падают, выдержать минимум 15 минут перед следующим раундом; за ночь максимум три таких раунда. Между ними выполнить независимую проверку кода. Расход диагностических запросов учитывать отдельно от исследовательских запусков.

### 2. Исправить подтверждённые дефекты и проверить реальный короткий цикл

Проверить прежде всего:

- Согласованность запрошенной схемы/фазы и реально возвращённого tool call. Вызов инструмента, отсутствующего в текущей схеме, должен получить контролируемую обработку; ограничение схемы в запросе само по себе не обеспечивает это.
- Сохранение текущего кода, гипотезы, измерений и corrective-инструкции при compaction. Текст о намерении изменить модель не считается изменением.
- Отдельный учёт reported tokens и консервативно списанного расхода, включая retry и resume. Прерванный запрос без сохранённой границы расхода не разрешает сброс бюджета.
- Ошибки сгенерированного кандидата должны возвращаться модели для ограниченного исправления. В smoke-v5 есть, например, `bagging_fraction` внутри CatBoost-конфигурации; этот кандидат не дошёл до проверки, его исполнимость не подтверждена.

Исправлять минимальный участок с регрессией на реальный сценарий. Проверять доступность изменений через вызывающий код, а не только отдельную функцию. Использовать только выданную Qwen; числовой поиск остаётся Optuna.

Первую полную проверку провести на изолированной копии diabetes: скопировать только четыре входных файла через `verification.verify_archive.copy_task`, не передавать worker файл holdout_targets.csv. Успешный smoke означает изменённый код, успешную full-валидацию, интерпретацию измерения и CSV, сопоставленный с финальным refit через `verify_run`. Один edit_file этого не подтверждает.

Если API мешает live, полезная независимая работа — ревью перечисленных границ, исправление подтверждённых дефектов, проверка verifier и документации. Не переписывать архитектуру и не наращивать тесты вместо проверки нужного поведения.

### 3. Пройти публичный gate на зафиксированном коде

После короткого цикла — `make check`, относящиеся тесты и один полный offline-прогон. Зафиксировать проверенные изменения коммитом и push в текущую ветку. Для серии выбрать новый каталог; сохранять все неуспешные попытки.

```sh
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 VECLIB_MAXIMUM_THREADS=1 \
uv run --locked --all-extras python -m verification.run_agent_comparison \
  data/regression/task.md data/classification/task.md \
  --gate --modes qwen --seeds 42 --sessions 3 \
  --output runs/nightly/gate-v1
```

Критерии каждого из двух запусков: код самостоятельно изменён Qwen; новый кандидат действительно прошёл full-валидацию; интерпретация соответствует измерению; итоговый CSV соответствует выбранному refit. Улучшение метрики для этого gate не обязательно. До принятия обеих задач серия сравнения закрыта. Проверить содержимое gate-report, а не только булево поле; runner позволяет передать произвольный набор задач.

Во время серии runtime и verification-код зафиксированы. После изменения исходников нужен новый gate, старый успешный report не переносится на новую версию. Тяжёлые эксперименты выполнять по одному, в установленных лимитах ресурсов.

Сопоставлять одинаковые protocol/seed/ресурсы. Control недоступен исследованию, diabetes test labels открывать только после полного cohort. Все попытки остаются в отчёте; ухудшение — допустимый честный результат. После просмотра финального control/holdout не подбирать по нему новые изменения.

Обновить этап 8 PLAN и этот статус фактами, путями к артефактам и ограничениями. Коммиты/push — в `fix/qwen-live-cycle`; merge в main и конкурсная отправка не входят в ночную работу.
