# Устройство агента

Агент решает табличную ML-задачу end-to-end: `python3 solution/solution.py task.md` → `submission.csv`. Обзор и запуск — в [README проекта](../README.md).

## Стратегия на максимальный балл

Балл = нормировка метрики против бейзлайна организаторов, хуже бейзлайна — 0.
Отсюда два приоритета: **никогда не падать** (упавший запуск = 0) и **выжать метрику**.

Каскад (каждая ступень перезаписывает `submission.csv`, файл существует с первой минуты):

0. **constant** — медиана/мода: страховка формата;
1. **quick_lgbm** (~минуты) — LightGBM с early stopping: уже сильнее типового бейзлайна;
1.5. **AutoEDA** (≤20 мин, `AGENT_AUTOEDA_SEC`; при нехватке времени пропускается):
   детекторы находят зависимости → гипотезы оформляются декларативными спеками
   DSL → единый валидатор принимает только то, что улучшает модель на фолдах,
   похожих на тест. Код признаков пишется один раз (`fe_dsl.py`), LLM и детекторы
   выдают только спеки.
   - `fe_dsl.py` — операции `group_stat` (таргет cross-fitted / признак), `group_dev`,
     `lag` (история объекта в прошлых периодах), `ratio/diff/prod`, `agg_cols`,
     `log/rank`, `count_enc`, `missing_ind`, `bin`, `interaction`, `knn_target`, `flag`, `drop`;
     `as_category` (целочисленный код как категория), `missing_count`, `date_parts`,
     `cyclic` (sin/cos периода); `group_stat` по таргету со сглаживанием (`smooth`)
     и переходом к общим ключам (`fallback`) для редких/неизвестных групп;
     модельные операции `segment_model` (отдельные модели на сегменты-режимы) и
     `objective` (huber/l1/fair для тяжёлого хвоста ошибок регрессии);
     исполнение fit → apply: на валидации fit = train фолда, в финале fit = весь train;
   - `eda_detectors.py` — 11 детекторов, у каждой спеки непрерывный `prior` (порядок
     оценки): **entities** (beam-поиск квази-ID объекта), **temporal** (период + лаги
     таргета по каждому кандидату ключа), **residuals** (ω² остатков OOF по колонкам,
     парам и путаемым парам классов), **categoricals**, **homogeneous** (группы имён
     `*_min/_avg/_max`, единицы словаря), **neighbors** (дубли, kNN-таргет, флаг
     label_copy, конфликты меток по классам), **segments** (естественные разделители —
     ноль, пропуск, уровни; смена корреляций и смещение остатков внутри сегмента,
     только точно эквивалентные разбиения схлопываются независимо от нумерации
     сегментов; вложенные разбиения проверяются отдельно), **tail** (доля ошибки в худших строках и
     что их объединяет), **missingness**, **transforms**, **shift** (adversarial validation);
   - Qwen, раунд 1 (`task_profile.llm_propose_specs`): 4 тематических промпта
     параллельно — время и объекты, сегменты, ошибки (хвост, перестановочная важность
     против корреляции, конфликты меток), семантика словаря; у каждого свои факты и
     список уже запланированных гипотез. Идёт в фоне, пока валидатор проверяет спеки
     детекторов. Раунд 2 (`llm_refine_specs`): Qwen видит итоги этапа A (дельты, что
     прошло) и развивает работающие направления. Все спеки — в тот же валидатор;
   - `fe_search.py` — фолды под тест (период → train на прошлом, val на последних
     периодах; новые объекты в test → GroupKFold; иначе (Stratified)KFold),
     детерминированный LightGBM; порог прироста калибруется по null-спекам
     (перемешанные копии топ-признаков); этап A — каждая спека против базы, этап B —
     жадный forward-отбор; признак с подозрительно идеальной метрикой отклоняется.
     Каждая спека попадает в журнал экспериментов. Принятые `segment_model`/`objective`
     переносятся в k-fold LightGBM для бленда, индикатор сегмента — признаком в AutoGluon;
   - идентичность DSL учитывает операцию, исходные имена колонок и все параметры:
     разные биннинги, пороги и числа соседей сохраняются одновременно. Перестановки
     аргументов коммутативных операций и ключей группировки объединяются;
     разность и отношение сохраняют порядок. Имена признаков содержат хэш этой
     идентичности, а коллизии обнаруживаются явно. Повторы гипотез и уже оценённых
     наборов используют прежний результат без повторного обучения;
2. **k-fold LightGBM** (`quick_oof`) на фолдах схемы cv — OOF-база и мерило
   стоимости для пула;
3. **пул рецептов** (`pool.py`, `AGENT_POOL_SHARE`=30% остатка): каждый рецепт —
   k-fold на тех же фолдах + frozen refit на всём train; допуск по профилю и
   прогнозу стоимости (кратно k-fold LightGBM), пропуск/сбой — в журнал:
   - регрессия: `log1p`/`sqrt` таргета при неотрицательном асимметричном таргете
     (обратное преобразование ровно один раз), Tweedie и двухчастная модель
     P(y>0)·E[y|y>0] при ≥10% нулей, `l1` под MAE, прогноз изменения от последнего
     таргета объекта (`delta`, при temporal-схеме и принятом `lag(target)`);
   - классификация Macro F1/F1: ранняя остановка LightGBM по метрике задачи;
   - ExtraTrees (bootstrap до 60k строк), XGBoost (hist, категории), регуляризованный
     LightGBM, CatBoost (TotalF1:Macro / AUC для остановки, Balanced для macro-метрик) —
     в порядке ценности на единицу стоимости; затем 2 seed лучшего рецепта и
     4 конфигурации LightGBM из каталога регуляризации/сэмплирования;
   - регрессия: если log1p/sqrt обошёл исходную шкалу, остальные семейства пула и
     AutoGluon обучаются в выигравшей шкале;
   - свободный текст (несколько слов, высокая уникальность): TF-IDF слов и
     символов + Ridge/LogisticRegression, матрица разреженная;
   после пула — промежуточный выбор и запись сабмита;
4. **autogluon** (остаток) — `TabularPredictor` c presets по бюджету времени
   (`best_quality`/`high_quality`/`good_quality`), eval_metric из профиля задачи;
4.5. **Поиск пары «модель + преобразование»** (`linear_search.py`, ≤60 с):
   для регрессии — Ridge на исходных числовых признаках и Ridge на исходных
   плюс `sign(x) * log1p(abs(x))`. Это отдельное семейство: отказ LightGBM от
   логарифма не отклоняет гипотезу для Ridge. Импутация медианой и стандартизация
   обучаются внутри каждого фолда; обе пары проверяются на одинаковых фолдах
   действующей схемы temporal/group/kfold. Идентичность пары включает семейство,
   колонки, преобразование и alpha. Выбранная пара переобучается на всём train;
   её OOF сравнивается с текущим победителем (включая существующий бленд) на
   всех его OOF-строках. Для замены нужен выигрыш >0,2%; при проигрыше, неполном
   покрытии, ошибке или таймауте остаётся текущий победитель. В журнале — выбор
   преобразования, рецепт, метрика и причина принятия/отказа.
   Ограничения первой версии: 20–100 000 размеченных строк, 1–200 числовых
   признаков; категориальные признаки Ridge не использует. Бюджет задаёт
   `AGENT_LINEAR_SEC` (0 отключает, максимум 60); резерв не отключает уже
   допустимый по времени запуск AutoGluon. Классификация следует прежнему каскаду;
5. **AutoResearch-постпроцессинг** — гипотезы принимаются только при улучшении OOF:
   - жадный ансамбль (Caruana, с возвращением) по всем оценённым кандидатам:
     модель вне двух лидеров входит, если улучшает смесь; дубли прогнозов пропускаются;
   - общие OOF-строки делятся на development (70%: состав/веса ансамбля, классовые
     множители) и control (30%, по группам при group-схеме) — аудит: смесь и
     множители принимаются, только если не хуже на control;
   - log loss: Platt (бинарная) / temperature scaling (мультикласс) по OOF,
     прирост проверяется 2-fold cross-fit; вероятности AutoGluon не перекалибруются;
   - классификация с macro-метрикой: координатный подбор классовых множителей
     вероятностей (сильно поднимает Macro F1 на дисбалансе);
   - регрессия: клиппинг предсказаний к диапазону таргета в train;
   - выбор источника, α бленда, веса классов и клиппинг — на общих OOF-строках
     кандидатов одной схемы валидации (см. «Независимая валидация»);
   - `label_copy_dups` (флаг детектора neighbors, классификация): метки точных дублей
     train без конфликта переносятся в test; ворота — LOO на train-дублях против OOF модели.

## Профиль задачи (универсальность для private-задач)

- id и целевые колонки — из `sample_submission.csv` (истина про формат);
- кросс-чек ролей по `data_dictionary.csv`;
- пути к данным — из текста task.md, иначе поиск рядом и рекурсивно;
- тип задачи и метрика — **LLM (Qwen через `OPENAI_*`) читает task.md**
  (до 2 попыток, строгий JSON); жёсткие факты из данных (dtype таргета,
  число уникальных) отсекают невозможные ответы LLM;
- без LLM: метрика — первое упоминание в тексте задачи, «регрессия» в тексте
  оставляет регрессией таргет с малым числом целых значений; последний рубеж —
  дефолты: регрессия → RMSE, мультикласс → Macro F1, бинарная → F1/accuracy;
- тип, метрика и формат вывода считаются отдельно для каждого таргета
  (`prof["per_target"]`); признаки AutoEDA одного таргета не переходят на другой;
- RMSLE → обучение на `log1p(y)`, оценка всех кандидатов — настоящий RMSLE;
- положительный класс бинарной задачи — `models.positive_label` (1/True,
  словарь yes/fraud/bad…, иначе последняя метка): одно правило для F1/AUC,
  весов классов и выходной вероятности;
- вывод вероятностей: бинарная задача с log_loss/roc_auc (заглушки sample
  не важны) или float-значения sample вне меток; колонки sample, которых нет
  в train, сопоставляются классам таргета по имени (`A`, `target_A`, `p_A`),
  иначе по порядку.

## Независимая валидация

Схема, выбранная AutoEDA (`fe_search.build_folds` → `prof["cv"]`: temporal по
периоду, group по ключу объекта или kfold), действует до конца конвейера:

- `models.outer_folds` — внешние фолды по той же схеме для k-fold LightGBM,
  quick-сравнения и AutoGluon; temporal: train — только прошлые периоды;
- ранняя остановка — на отдельной части train фолда (`es_split`), не на оцениваемом фолде;
- признаки из таргета (`group_stat`/`lag` по таргету, `knn_target`) не пишутся
  в train: `models.target_features` строит их заново в каждом фолде (fit = train
  фолда), внутренний cross-fit (`fe_dsl.inner_splits`) тоже соблюдает схему —
  только прошлые периоды, чужие группы. AutoGluon получает их только при temporal
  (признаки строятся по прошлому); при kfold/group бэггинг протёк бы через них;
- AutoGluon бэггит по тем же фолдам (`groups`); при temporal — holdout-fit на
  прошлом с оценкой на последнем периоде, затем fit на всём train для test;
- OOF кандидатов сопоставляются по индексам строк train и порядку классов
  (`solution.align_candidates`); строки без OOF исключаются, расхождение
  таргета — ошибка;
- test предсказывает модель, обученная на всём размеченном train.

## Журнал экспериментов

`experiments.jsonl` рядом с task.md: строка на каждый эксперимент (гипотеза,
таргет, метрика, схема проверки, скор, длительность, решение, причина отказа
или ошибки), дописывается сразу — доступен после сбоя.

## Точные ключи

`eda_probe.normalize_keys`: целые — десятичной записью без float (большие
int64 не склеиваются), 1942 и 1942.0 совпадают, пропуск — отдельный уровень,
компоненты составного ключа хэшируются раздельно. Перенос меток дублей
сверяет точные строки ключей (`row_key_strings`), а не хэши.

## Запись результата

`write_submission` собирает файл по контракту (колонки и порядок sample,
id и порядок строк test, конечность, вероятности в [0, 1], сумма строки = 1),
пишет во временный файл и заменяет `submission.csv` через `os.replace`.
Не прошедшая проверку версия не пишется: остаётся предыдущий валидный файл,
предсказания в памяти откатываются. Неоценённый кандидат (метрика не
посчитана) не участвует в выборе; целевая метрика не подменяется accuracy.

Тесты (синтетика, без LLM; `test_autogluon.py` пропускается без autogluon —
для него добавить `--with "autogluon.tabular[lightgbm]==1.3.1" --with typing_extensions`):

```bash
cd solution && uvx --python 3.12 --with numpy==1.26.4 --with pandas==2.2.3 \
  --with scikit-learn==1.5.2 --with lightgbm==4.6.0 --with scipy==1.12.0 \
  --with psutil==6.1.1 pytest tests -q
```

## Тайм-менеджмент

Бюджет 3 ч (`AGENT_TIME_LIMIT_SEC` для локальных тестов), запас 7 мин
(`AGENT_SAFETY_SEC`) + резерв 8 мин на predict (`AGENT_PREDICT_RESERVE_SEC`).
Каждый таргет работает до абсолютного времени окончания (`solve_target`:
`t_end`), этапы получают остаток от него. Ограничители:

- сторожевой поток (`agent_utils.start_watchdog`) за `AGENT_HARD_MARGIN_SEC`
  (2 мин) до лимита убивает дочерние процессы и завершает процесс с кодом 0 —
  на диске остаётся последний валидный `submission.csv`;
- AutoEDA — под `time_limit` (SIGALRM, бюджет × 1.25 + 60 с) на копии профиля;
  тяжёлые этапы остаются в главном потоке: LightGBM в рабочем потоке в 2,5–8
  раз медленнее из-за пулов OpenMP;
- LightGBM — callback `time_guard` по дедлайну (quick, k-fold, валидатор AutoEDA);
- LLM — каждый вызов ограничен по времени в daemon-потоке;
- в конце `os._exit` после остановки дочерних процессов: фоновые потоки не держат процесс;
- CPU — `available_cpus()`: affinity и квота cgroup (`AGENT_N_CPUS` — вручную).
AutoGluon получает остаток. Мульти-таргет — бюджет каждого таргета = фактический
остаток времени / число оставшихся таргетов.

## Проверка поиска «модель + преобразование» (#6)

Парное сравнение с `aab56fd` (до добавления Ridge): по три разбиения на шести
задачах, оценивается итоговый CSV на holdout, метки которого лежат вне каталога
задачи. На diabetes средний RMSE 56,635 → 54,308; на логарифмической синтетике
0,555 → 0,392; на линейной — 14,153 → 0,428. На нелинейных сегментах и обеих
публичных задачах соревнования метрики не изменились: там агент сохраняет
прежний источник. Это короткие локальные прогоны без LLM и AutoGluon;
результат не является оценкой скрытого теста соревнования.

Метрики каждого разбиения, время, пиковая RSS-память, причины выбора и хэши
исходников — в [verification/issue6-results.json](../verification/issue6-results.json).
Скрипт [verification/compare.py](../verification/compare.py) запускает обе версии
с одинаковыми настройками, без настроек агента для отдельных датасетов:

```bash
python verification/compare.py --baseline /path/to/old/solution --candidate solution \
  --output .scratch/benchmarks/issue6-local --seeds 17 29 43 \
  --tasks log_regression linear_regression diabetes nested_segments
python verification/compare.py --baseline /path/to/old/solution --candidate solution \
  --output .scratch/benchmarks/issue6-public --seeds 17 29 43 \
  --tasks public_regression public_classification --public-root data --budget 420 --autoeda 90
```

Эти команды выполняются из корня репозитория. В локальном окружении нужны
пакеты из команды тестов выше; AutoGluon для воспроизведения этого замера не
устанавливается. Ветки независимой валидации проверены unit-тестами temporal/group;
публичная регрессия дополнительно оценивается на следующем годе: train — годы
1–4 (до 15 000 строк), holdout — год 5 (до 6 000 строк).

## Эксперимент: повторяющийся цикл исследования

Режим `AGENT_RESEARCH_MODE=iterative` включает `research_search.py`. По умолчанию
остаётся прежний режим `legacy`: пилот на задачах Альфы дал выигрыш в регрессии
и ухудшение в классификации.

Локальное сравнение на публичных задачах Альфа-Банка с Qwen и номинальным
лимитом исследования 10 минут: [результаты и ограничения](../verification/alfa-research-results.md),
[метрики отдельных запусков и хэши](../verification/alfa-research-results.json).

Цикл хранит до четырёх рецептов: исходный, текущий лидер и альтернативы, в том
числе варианты, пока уступающие лидеру. Каждый раунд диагностирует OOF-ошибки
выбранного рецепта; после улучшения следующая диагностика относится к новому
лидеру. Qwen получает свежие ошибки, текущие преобразования и историю проверок.
Следующий эксперимент добавляет признак к выбранному рецепту или заменяет его
модельную операцию. Вариант, проигравший отдельно, может выиграть в сочетании.

Для новой пары сначала проверяется один фиксированный фолд. Перспективные
варианты и четверть остальных попыток проходят все фолды; только полная оценка
может сменить лидера. Порог калибруется по перемешанным признакам, требуется
положительная нижняя оценка прироста по фолдам. Ранняя остановка по оцениваемому
фолду отключена: валидатор обучает фиксированные 500 деревьев, а метки внешнего
фолда используются только после предсказания. Temporal/group-схема остаётся
фиксированной; диагностика видит лишь строки с допустимым OOF.

Ограничения первой версии: 24 раунда, до 144 уникальных наборов, до 8 вызовов
предложения гипотез Qwen и до 8 спек в рецепте. Одна JSON-попытка может быть
повторена клиентом; фактическое число ответов и токены пишутся в лог.
Кэш матриц ограничен 16 спеками. Остановка по времени сохраняет последний
завершённый рецепт. Эквивалентные наборы не обучаются повторно.

`research/<hash-target>.json` рядом с задачей атомарно сохраняет рецепты,
родительские связи, оценки, историю лидеров и причины отказов/остановки. Это
журнал результатов, а не механизм возобновления процесса. Принятый рецепт
переносится в обычное финальное обучение через общий `apply_recipe`.

Для длительного исследования можно выделить до 90 минут:

```bash
AGENT_RESEARCH_MODE=iterative AGENT_AUTOEDA_SEC=5400 AGENT_RESEARCH_SHARE=0.75 \
  python3 solution.py /path/to/task.md
```

`AGENT_RESEARCH_SHARE` — доля свободного времени после резервов финального
обучения и предсказания (для iterative по умолчанию 0,75, допустимо 0,1–0,9).
`AGENT_AUTOEDA_SEC` остаётся верхней границей. Лимит не требует тратить всё
время: исчерпание гипотез или числа попыток завершает поиск раньше.

Для совместимого LLM-провайдера используются `OPENAI_API_KEY`, `OPENAI_BASE_URL`
и `OPENAI_MODEL`. Необязательные ограничения: `AGENT_LLM_MAX_TOKENS`,
`AGENT_LLM_REQUEST_SEC`, `AGENT_LLM_REASONING_TOKENS` либо
`AGENT_LLM_REASONING_EFFORT`. Параметр reasoning передаётся в `extra_body` и
должен поддерживаться провайдером; при указании двух вариантов приоритет
у явного бюджета токенов. Учёт usage и finish_reason помогает отличать
отсутствие полезных гипотез от обрезанных ответов или таймаутов.

Сравнение исследовательских бюджетов выполняет
[verification/research_curve.py](../verification/research_curve.py). Протокол
записывается до запусков: данные, seeds, бюджеты, модель LLM и хэши исходников.
Оба режима получают одинаковый доступ к LLM; финальное обучение и выбор CSV
в этом стенде одинаковы, AutoGluon не используется. Метки внешнего holdout
недоступны агенту. Для каждого лимита выполняется отдельный запуск; отчёт
содержит и лимит, и фактическое время. Это сравнение исследовательских циклов
на общем стенде, а не оценка полного трёхчасового каскада платформы.

```bash
python verification/research_curve.py --source solution --output .scratch/research-alfa \
  --tasks public_regression public_classification --seeds 17 29 --budgets 600 \
  --max-train-rows 100000 --max-test-rows 100000 --final-fit-seconds 600 \
  --credentials-file /path/to/local-credentials.json
```

Эта команда использует полные локальные разбиения публичных задач Альфа-Банка,
исходные имена таргетов, условия и словари. Для регрессии контроль — год 5;
повторы меняют порядок тех же строк, поэтому это один временной holdout.
Для классификации — два стратифицированных разбиения 80/20. Более длинные
лимиты задаются через `--budgets 600 1800 5400`; резерв финального обучения
измеряется отдельно от исследования.

Файл credentials содержит только стандартные `OPENAI_*` переменные и не
копируется в протокол или каталоги задач. Автоматическое объединение веток
рецептов, ансамбль из всего портфеля, изменение целевой переменной и модели
нулевой/ненулевой части ответа остаются следующими этапами.

## Сравнение полного каскада с AutoGluon

[verification/full_cascade.py](../verification/full_cascade.py) запускает рабочий
`solution.main` в обоих режимах: исследование, AutoGluon, LightGBM по фолдам,
выбор/смесь и постобработка. Оба получают 3000 секунд общего времени;
исследование ограничено 600 секундами и долей 0.3. Остаток используется каскадом
по обычным правилам. Это отдельный протокол от исследования без AutoGluon.

```bash
python verification/full_cascade.py --source solution \
  --output .scratch/benchmarks/alfa-full-cascade \
  --credentials-file /path/to/local-credentials.json \
  --tasks public_regression public_classification --seeds 17 29 \
  --total-seconds 3000 --jobs 2
python verification/summarize_full_cascade.py .scratch/benchmarks/alfa-full-cascade \
  --output verification/alfa-full-cascade-results.json
```

Выходной каталог должен быть новым. Сводка создаётся после всех запусков,
проверяет хэши кода и входов, одинаковые данные в паре, отсутствие контрольных
меток во входном test и пересечений ID train/holdout. Валидный CSV, завершённый
каскад и фактически оценённый AutoGluon учитываются раздельно. Дополнительный
CSV AutoGluon сохраняется до смешивания и постобработки; это компонент того же
запуска, а не самостоятельный контроль с равным бюджетом.

Протокол, ограничения среды и разбор выбора моделей — в
[отчёте полного каскада](../verification/alfa-full-cascade-results.md).

В завершённом 50-минутном сравнении (8 запусков) средняя RMSE изменилась
с 40.3355 до 43.4716, Macro F1 итоговых CSV — с 0.66948 до 0.64199.
Все CSV валидны, но в двух запусках классификации общий дедлайн прервал
AutoGluon и сохранилось резервное решение. На втором разбиении классификации
оба каскада завершились, и iterative выиграл 0.92 п.п. Стабильного общего
выигрыша нет; новый режим остаётся экспериментальным. Это локальный holdout,
не официальный скрытый test и не стандартный трёхчасовой бюджет платформы.
