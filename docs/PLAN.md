# План реализации

Этапы выполняются последовательно. Каждый заканчивается проверяемым результатом; следующий этап начинается после его проверки. Подготовительный коммит отделён от реализации агента.

Готовность: удалённая ветка содержит scaffold и план, локальное окружение воспроизводится через `make setup`. Исследовательская логика пока отсутствует.

Проверено локально на macOS arm64: `make check`, `uv pip check`, загрузка Qwen SDK/ML-библиотек/AutoGluon, соответствие 18 runtime-требований списку организаторов, `python -S solution.py --help`. Python 3.12.12, uv 0.9.17. Linux-проверка и обучение относятся к следующим этапам; тестов поведения пока нет.

## 1. Контракт задачи и модель эксперимента

- [x] Реализовать domain-типы, сравнение Score с направлением метрики, статусы Experiment и Budget.
- [x] Реализовать чтение материалов задачи и проверку TaskSpec по данным/словарю/sample submission.
- [x] Добавить сценарий prepare_task и необходимый TaskData port.
- [x] Определить validation protocol: random/stratified/group/time по условию и структуре; фиксировать индексы и fingerprint.
- [x] Добавить небольшие синтетические фикстуры и тесты регрессии, numeric labels, binary/multiclass, групп/времени и противоречивого формата.

Готовность: обе публичные задачи описываются единым контрактом без хардкода target; противоречия имеют явную диагностическую ошибку. Метрики разных протоколов нельзя случайно сравнить.

Проверено 19.10.2026: `make check`, `make test` (110 тестов), повторная подготовка обоих оригинальных публичных task.md с seed=42. Регрессия: 53 308/22 449 train/test, random 42 646/10 662; классификация: 87 670/41 166, stratified 70 137/17 533. Индексы и fingerprints сохранены локально в `runs/stage1/{regression,classification}.json`; повторная подготовка даёт тот же контракт и split. CSV и исходные task.md не изменены и не входят в Git.

Контракт извлекает метрику из явного описания, схему/таргет/ID из словаря и файлов; поддерживает структурированное уточнение `task-json`. Неоднозначные метрики и противоречащие декларации отклоняются с ContractError. Произвольное естественно-языковое описание потребует Qwen-уточнения на этапе 3; такой случай не разрешается молчаливой догадкой. Smoke/full и разные протоколы несопоставимы. Публичное описание не требует прогнозирования будущего года; Year_Factor сам по себе не является основанием для time split. Group/time выбираются по роли словаря или явному указанию колонки.

Готовность: один вызов solution.py на каждой публичной задаче создаёт корректный CSV, использует фиксированный split, не требует установки/сети во время работы модели. Это ещё не агент, но сквозной путь уже работает.

Проверено 19.10.2026 на macOS arm64: `make check`, `make test` (179 тестов), полный `solution.py` для обоих оригинальных публичных task.md, backend CatBoost, 8 threads. Regression: RMSE 42.8280212835, validation/refit 1.87/2.11 s, CSV 22 449 строк. Classification: Macro F1 0.5545846003, validation/refit 56.02/70.94 s, CSV 41 166 строк. Это локальные validation-метрики, не скрытый score платформы. Журналы, frozen prepared.json и результаты: `runs/stage2/public-{regression,classification}/`. CSV повторно проверены отдельно по схеме, ID, порядку и допустимым значениям.

Оба backend проверены с маленькими моделями на пропусках/неизвестных категориях и numeric/string labels. Worker сохраняет строковые ID, включая ведущие нули и NA; ID не участвует в обучении. Тесты подтверждают deadline и завершение порождённого процесса, ограничение RSS, отсутствие OPENAI_/QWEN_ в worker, сохранность старого CSV при неверных предсказаниях и ошибке atomic replace, .env без override окружения. Метрики считаются evaluator из исходных validation targets, а не stdout. Linux/8 CPU/32 GB и условия платформы пока не проверены — этапы 6–7; онлайн-установка и сетевые вызовы в модельном коде отсутствуют, испытание с запрещённой сетью относится к упаковке.
