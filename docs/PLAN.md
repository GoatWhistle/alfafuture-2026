- [x] Проверить перезапуск процесса и повторные/сломанные записи без дублирования завершённых запусков.

Готовность: серия экспериментов переживает перезапуск; следующая сессия видит прошлые неудачи и работает в ограниченном контексте независимо от длины полного журнала.

Независимая от выданного endpoint часть завершена 19.10.2026 при открытом live-блокере этапа 3 (по разрешению продолжать независимые задачи). `make check`, `make test`: 321 offline-тест. JSONL хранит started/finished события, parent/гипотезу/параметры и их hash, data/protocol fingerprints, smoke/full score, error-report поле, время и пути артефактов. Session-события отдельно хранят интерпретацию и usage с флагом известности; расход на несколько попыток одной сессии помечается shared_session, без выдуманной атрибуции одному эксперименту.

Проверены fsync/flock, одинаковые/конфликтующие дубли, quarantine оборванного хвоста и явный отказ на повреждённой средней записи. Код хранится по SHA256 с проверкой целостности; завершённые артефакты read-only для обычного исполнения (это не security sandbox). Завершённый эксперимент восстановлен в новом Python-процессе с runner, который падает при любом повторном вызове; повторного обучения нет. Готовый full-result после разрыва перед terminal-событием восстанавливается независимой оценкой. Живой worker проверяется по PID + create_time через psutil, а не объявляется остановленным из-за старого state-файла.

`--resume --run-dir ...` проверяет fingerprint и готовый CSV, восстанавливает baseline без обучения; это отдельно подтверждено на публичной регрессии (`runs/stage4/resume-regression/`, неизменные request mtime и CSV SHA256). Новый запуск в занятом каталоге отклоняется, lease удерживается весь CLI. До завершения baseline resume требует валидный baseline.json/CSV и выдаёт явную ошибку при их отсутствии. Две fake-гипотезы прошли реальные worker в новых коротких сессиях; вторая получила измеренный результат и отдельную интерпретацию первой. Начальный JSON-контекст <=12 000 символов, история обращений <=48 000 символов независимо от размера журнала; это лимиты символов, не подтверждённый лимит токенов endpoint.

Готовность: журнал позволяет показать конкретную цепочку «ошибка → гипотеза → изменение → измеренный эффект». Отсутствие улучшения тоже корректный результат, а не повод менять оценщик.

Проверено 19.10.2026: `make check`, `make test` — 403 offline-теста, live-тест не входил в запуск. Этап 5 выполнен как независимая offline-часть при сохранённом live-блокере этапа 3. Критерий цепочки проверен на реальных worker и публичных CSV; происхождение гипотез явно `offline_scripted_verification`, не Qwen.

Диагностика независимо проверяет ID и считает confusion matrix/дельту, precision/recall/F1/support и парные переходы правильности. Для регрессии — RMSE/MAE/bias по сегментам, границы quartile bins и top-категории выводятся только из train partition. По умолчанию нужны >=30 объектов и в train, и в validation; исследуются первые 20 признаков, до 8 категорий на признак, ограничения/пропуски покрытия явно записаны. Пустая ячейка является пропуском; текст NA остаётся категорией. Score и segment/class deltas считаются на одних validation IDs, интерпретация отделена. Baseline и parent predictions проверяются по hash; перед новой гипотезой восстанавливается именно выбранная версия родителя. Сохраняются альтернативы, лучшие хотя бы на одном устойчивом сегменте, даже при худшем общем score; каждая третья сессия может продолжить такую ветку.

На фиксированном публичном regression protocol `a8009b17...` (`runs/stage5/regression/`): baseline RMSE 42.8280212835; capacity 42.4599100385; LightGBM 40.8403722904; signed-log target 44.3148586058 (parent=capacity, ухудшение +1.8549485674); train-only tuning 44.0967854108 (3 trials, ухудшение относительно baseline). У Commercial_Other (n=230) LightGBM снизил MAE на 2.9565539770 и RMSE на 4.3945236041 относительно baseline. Signed-log сохранился как альтернатива: несмотря на худший общий RMSE, он лучше на некоторых сегментах по MAE; это наблюдение, не доказательство причинности.

На публичном classification protocol `8ea34a66...` (`runs/stage5/classification/`): balanced class weights дали Macro F1 0.5420596739 против baseline 0.5545846003 — не улучшение. У DoS (n=1226) F1 вырос на 0.1693533210; у Backdoor/Analysis вырос recall, но упала precision и F1. Журнал хранит эти расхождения, evaluator не менялся. Команда воспроизведения: `uv run --locked python -m ml_harness.entrypoints.verify_research TASK BASELINE_RUN OUTPUT_RUN`; `--hypotheses class_balance` ограничивает проверку одной гипотезой. Это проверка механики исследования, а не сравнение полного агента при равных ресурсах (этап 7).

Optuna: 1–10 trials, time_limit<=300 s, n_jobs=1, inner split только внутри переданной train части с random/stratified/group/time. Проверка с изменёнными outer-validation targets дала те же trials и predictions; неудачные trials сохраняются в tuning.json даже при падении всего кандидата. Начатый trial ограничивается hard deadline runner, timeout Optuna лишь прекращает старт новых trials. Full-метрика отдельно считается evaluator; inner-метрика не ранжируется с full. Выбранные параметры/fingerprint сохраняются отдельно от исходных factory arguments.

AutoGluon 1.3.1: только CAT/GBM/XGB, CPU, без предобученных моделей/скачиваний, bagging/stacking/dynamic stacking/weighted ensemble отключены. Использует метрику и внутреннюю group/time-схему задачи, затем refit_full лучшей модели на всех переданных train rows. Реальные маленькие regression/binary/multiclass fit проверили выбранную *_FULL и num_samples=100; шестиметричная матрица и resource propagation дополнены fake-проверками. Артефакты остаются в рабочем каталоге worker.

Готовность: процесс сохраняет рабочий ответ при сбоях; истечение бюджета не оставляет частично записанного файла. Тестируется Linux, а не только macOS.

Промежуточная проверка 19.10.2026: `make check` и 584 offline-теста проходят на macOS arm64. Общий дедлайн включает импорт entrypoint; поиск использует измеряемый резерв, API retries/output ограничиваются остатком, resume сохраняет исходный deadline и накопленный usage. Неизвестный usage прекращает последующие API-вызовы. Токенный резерв запроса распределяется на все разрешённые retries; успешный ответ после retry не скрывает неизвестную стоимость предыдущей попытки. Started-сессия без finished-события после прерывания также считается unknown usage: resume не обнуляет потенциально потраченные токены и не создаёт новый API adapter. Это отдельно проверено имитацией разрыва внутри model.complete. До тяжёлого worker атомарно сохраняется валидный статистический либо существующий CSV; контрольные строки не участвуют в этом fallback и профиле исследовательских tools.

`runs/stage6/public-regression/`: исходные 53 308 строк разделены на 38 382 train / 9 595 development / 5 331 control. ## 9. Управляемое исполнение гипотез (20.10.2026)

### Основание и результат

На исходной точке `4e887d3` базовый ML-путь работает, `make check` и повторный
offline-прогон проходят: 629 passed / 1 live deselected. Публичный gate-v7
не принят, сравнение — 0/18. Это статус до изменений.

Проблема шире доступности API. В classification gate-v7 все шесть API-вызовов
завершились, но кандидат сначала использовал недопустимый CatBoost eval_metric,
затем превысил timeout. Кроме того, бюджет в контексте Qwen устаревает внутри
сессии; исходный код обрезается до вычисления флага truncation; обязательный
review расходует остаток бюджета после измерения. Старый verifier принимает
непустой summary за интерпретацию и недостаточно проверяет состав live-gate.

Цель: завершать полезные проверяемые эксперименты при ограниченном бюджете.
Qwen выбирает изменение по измеренным ошибкам и получает факты для следующего
шага. Harness отвечает за исполнимость, ресурсы, оценку и сохранность результата.
Улучшение метрики проверяем отдельно от работоспособности цикла.

### Новый порядок

1. Подготовить задачу и фиксированную валидацию, обучить baseline, сразу сохранить CSV.
2. Передать Qwen ошибки, измеренные затраты, доступные действия и свежий бюджет.
3. Получить одну структурированную гипотезу: родитель, целевая ошибка/сегмент,
   объяснение, ожидаемый эффект и конкретное изменение.
4. Проверить предложение, материализовать исполнимый рецепт, выполнить smoke,
   оценить стоимость полного обучения и принять решение о допуске.
5. Выполнить full, независимо измерить score, дельту к родителю, изменения ошибок
   и затраты; сохранить факты до следующего обращения к Qwen.
6. Повторять при наличии бюджета; целевой объём первой версии — 2–3 завершённых
   эксперимента, максимум три гипотезы за запуск. Сбои/нехватка бюджета могут
   уменьшить фактическое число; попытки и успешные измерения считаются раздельно.
7. Выполнить существующий финальный отбор/refit и атомарно сохранить CSV.
   Итоговое текстовое объяснение допустимо только после сохранения результата
   и при остатке бюджета. Отказ, пустой ответ или ошибка объяснения не отменяют CSV.

### 9.1. Контракт предложения и границы исполнения

- [ ] Добавить типизированные Proposal/ResolvedExperiment и результат валидации
      с явными причинами отказа. Domain/application — stdlib dataclass/Protocol;
      схемы внешних сообщений и SDK остаются в adapters.
- [ ] Предложение содержит parent ID, ссылку на измеренную ошибку либо явно
      обозначенную исследовательскую гипотезу, rationale, expected effect,
      явные task kind и backend, конфигурацию/преобразование признаков.
      Не допускать неявного выбора backend по имени типа задачи.
- [ ] Для штатных изменений использовать структурированную конфигурацию:
      поддерживаемый backend, разрешённые параметры и преобразования.
      Валидация типов, диапазонов, сочетаний и совместимости с задачей проходит
      до worker. Не передавать произвольные kwargs модели без проверки.
- [ ] Seed, потоки, метрика оценки, split, пути и ресурсные ограничения принадлежат
      harness; предложение не может их переопределить. Training objective и
      внутренние метрики backend допускаются только из совместимого allowlist.
- [ ] Сохранить генерацию Python для новых преобразований признаков.
      Определить минимальный fit/transform контракт: fit только на текущем train,
      одинаковая схема и порядок строк на validation/test, без доступа к их targets.
      Исполнение — в существующем worker с его ограничениями; это не заявление
      о полноценной песочнице для враждебного Python.
- [ ] Материализация обычного рецепта не требует генерации model factory Qwen.
      Сохранить requested proposal, resolved spec, effective code и hashes;
      дедупликация учитывает фактически исполняемый рецепт.

Приёмка: валидное предложение становится воспроизводимым кандидатом; неверная
метрика/backend/параметры отклоняются до обучения. Реальное новое преобразование
проходит fit/transform и frozen refit без утечки и нарушения строк.

### 9.2. Допуск по ресурсам и актуальный бюджет

- [ ] Перед каждым LLM-запросом и тяжёлым действием пересчитывать фактические
      remaining seconds/tokens, резерв финализации и допустимую стоимость шага.
      Учитывать API retries и неопределённый usage по существующей схеме.
- [ ] Исправить раннее обрезание исходника и ложный truncation flag; в компактном
      состоянии сохранять parent/backend, рецепт, измеренные ошибки и затраты.
- [ ] Использовать baseline timings и короткий smoke для оценки full-cost:
      учитывать backend, размер данных и сложность рецепта. Не считать линейную
      экстраполяцию по числу строк гарантией; сохранять метод/допущения оценки,
      safety factor и фактическую ошибку прогноза после исполнения.
- [ ] До full проверять прогноз против оставшегося search budget и worker timeout.
      Недопустимый рецепт отклонять с численной причиной. Если реализовано
      автоматическое уменьшение сложности, политика детерминирована, отражена
      в resolved spec и сообщается Qwen; никаких скрытых подмен параметров.
- [ ] Сохранять жёсткий deadline worker и остановку дерева процессов независимо
      от прогноза. Failed workers расходуют время, но не становятся успешной
      калибровкой refit. Ранний CSV переживает ошибку/таймаут/исчерпание бюджета.

Приёмка: тесты с управляемыми часами показывают свежий бюджет после API/worker;
заведомо дорогой рецепт не запускает full; ошибочная оценка ограничивается
deadline и сохраняет CSV. Резерв покрывает финализацию до необязательного текста.

### 9.3. Цикл исследований и численный поиск

- [ ] Заменить критический путь read/edit/run/interpret/review на
      propose → validate → smoke/admit → full → persist measured result.
      Ограничить исправления: не более двух коррекций одной гипотезы;
      повторная идентичная неудача не запускает тот же worker заново.
- [ ] Qwen выбирает смысловое изменение по ошибкам: признаки, допустимую обработку
      групп, семейство/стратегию модели. Численный подбор поручается существующей
      Optuna внутри явно выделенного бюджета, без LLM-вызова на каждый trial.
      Подобранные параметры фиксируются для full/refit; повторного поиска
      при refit нет. Inner tuning не использует outer validation/control.
- [ ] Для каждого эксперимента атомарно сохранять статус, parent, proposal/spec/code
      hashes, фактический backend, score/parent delta, сопоставимый error delta,
      время и usage. Неизмеренный показатель обозначать отсутствующим.
- [ ] Следующее предложение получает эти факты и отказ предыдущей попытки.
      Комментарии Qwen хранятся отдельно и не изменяют измеренные поля.
- [ ] Удалить обязательный LLM-review из условий завершения/успеха.
      Финализация и CSV предшествуют необязательному итоговому объяснению.
- [ ] Сохранить resume, дедупликацию, validation/control изоляцию, ранний CSV
      и frozen refit. Старые журналы либо читаются явно поддерживаемым способом,
      либо отклоняются как несовместимые без перезаписи и ложного resume.

Приёмка: scripted integration проходит минимум два последовательных изменённых
full-эксперимента; второй использует факты первого. Отказ API на последующем
шаге/объяснении не теряет измерения и финальный файл. Отдельно проверяется
численный поиск и воспроизводимость выбранного рецепта при refit.

      фактически изменённый и успешно измеренный full-эксперимент.

- [ ] Добавить отрицательные тесты: отсутствующая задача, пустой cohort,

### 9.5. Live и измерение пользы

- [ ] После offline — короткий smoke на diabetes без просмотра holdout, затем
      новый публичный gate в `runs/pipeline-v2/` с неизменными исходниками.
      Старые gate не переиспользовать и не перезаписывать.
- [ ] Сначала одна серия gate. После воспроизводимого исправления конкретного
      дефекта допустима ещё одна свежая серия; максимум две серии за эту передачу.
      При повторяющихся provider errors сохранить диагностику и завершить
      доступную offline-работу, не устраивать бесконечные запросы endpoint.
- [ ] Только после принятого gate запустить прежнюю матрицу 18 последовательных
      запусков: public regression/classification и diabetes, seeds 7/42/2026,
      Qwen против портфеля с Optuna. Общие ceilings: 1800 s, 4 threads,
      6000 MiB, worker timeout 300 s; Qwen — 32 000 tokens и максимум три
      гипотезы вместо прежних 12 сессий. Заморозить лимиты до старта cohort.
- [ ] Сохранить равные wall/CPU/RAM ceilings для обоих режимов, весь API overhead
      входит во время Qwen. Control не передавать исследовательскому циклу;
      diabetes holdout оценить только после полного cohort.
- [ ] Отчёт различает надёжность (completed full, CSV, затраты) и пользу
      (парный прирост score). Прежний критерий пользы: положительный средний
      относительный прирост минимум на двух задачах и положительное общее
      среднее. Три seed дают описательное сравнение, не статистическое доказательство.
      Частичный cohort/непройденный gate не выдавать за завершённую приёмку.

Этап закрывается только по выполненным критериям с артефактами и командами.
Неудачный live или отсутствие выигрыша — допустимый фактический исход отчёта,
но не основание отметить соответствующие пункты выполненными.
