# Усиление AutoResearch для конкурсных задач

## 1. Цель и выбранный подход

Сохранить работающую основу и поэтапно получить систему, которая надёжно завершает запуск и улучшает качество на незнакомых табличных задачах. Каждый этап проверяется отдельно; календарные сроки не задаём.

Текущая база пригодна для развития: 651 offline-тест проходит, есть независимый evaluator, ограничения worker, журнал, восстановление, ранний CSV и финальное переобучение. Основные ограничения находятся в исследовательском цикле:

- Qwen не получает полноценный профиль данных и словарь признаков.
- Численный поиск не продолжает найденные Qwen преобразования.
- Поиск ограничен тремя гипотезами независимо от остатка ресурсов.
- Управление исследованиями распределено между entrypoint, LLM-адаптером и большим ResearchWorkspace.
- Для классификации сохраняются метки вместо вероятностей, что ограничивает ансамблирование.
- Контрольная выборка используется при выборе финалиста, поэтому её score недостаточен для независимого доказательства пользы всей системы.

Основной вариант — управляемый гибрид: Qwen предлагает содержательные изменения; численный поиск настраивает весь обучаемый pipeline; общий исполнитель отвечает за данные, бюджет, измерения и сохранение результата.

Проверенные альтернативы:

| Вариант | Что полезно | Решение для проекта |
|---|---|---|
| AutoGluon как основной движок | Готовые механизмы обучения нескольких моделей, bagging, ансамблей и refit | Добавить полноценный сравнительный режим с разрешёнными моделями. Текущий ограниченный AutoGluon-кандидат не представляет всех возможностей движка. |
| FLAML как основной поиск | Поиск моделей и параметров с учётом стоимости вычислений | Добавить сравнительный режим; проверить, выигрывает ли он у собственного численного поиска. |
| Свободная генерация программ по подходу AIDE | Разные исходные решения, дерево улучшений и ограниченный ремонт | Использовать принципы ветвления и одного содержательного изменения на эксперимент. Полную генерацию скриптов основным путём пока не делать. |
| Собственный гибрид | Прозрачный бюджет, независимая оценка, развитие найденных признаков, измеримый вклад Qwen | Основной путь реализации. |

Основания: AutoGluon 1.3.1 (https://auto.gluon.ai/1.3.1/api/autogluon.tabular.TabularPredictor.fit.html), FLAML 2.3.6 (https://raw.githubusercontent.com/microsoft/FLAML/v2.3.6/flaml/automl/automl.py), AIDE (https://arxiv.org/html/2502.13138v1). Выбор гибрида — инженерная рекомендация; превосходство по качеству предстоит измерить.

## 2. Архитектурные изменения

### Единое управление исследованием

Перенести последовательность «выбрать следующий шаг → предложить рецепт → проверить → исполнить → сохранить результат» в application-сценарий.

- Entry point собирает зависимости и запускает сценарий.
- LLM-адаптер отвечает за транспорт, схему ответа и usage.
- Планировщик выбирает следующий шаг по истории и доступным ресурсам.
- Исполнитель одинаково выполняет рецепты от Qwen и численного поиска.
- Хранилище сохраняет события и артефакты; evaluator независимо вычисляет метрики.

Разделять существующий ResearchWorkspace по этим обязанностям постепенно, без создания интерфейса для каждой вспомогательной функции. Существующие runner, evaluator и атомарную запись CSV сохранить.

### Единый исполняемый рецепт

Развить текущий ResolvedExperiment в каноническое описание полного pipeline:

- преобразования признаков;
- backend и параметры модели;
- настройки внутреннего поиска;
- правило получения предсказания из вероятностей;
- зафиксированный результат настройки для повторного обучения.

Qwen и Optuna должны изменять один и тот же рецепт. Потомок наследует фактически исполненный pipeline родителя, включая признаки и подобранные параметры.

Создать единый каталог возможностей backend: допустимые параметры, диапазоны, типы задач и ограничения. Из него получать схему для Qwen, проверку рецепта и описание пространства поиска. Это устранит расхождения между prompt, валидацией и фактическим исполнением.

Внутренние контракты: DatasetProfile, PipelineRecipe, ExperimentResult, SearchDecision. В domain/application — dataclass и стандартная библиотека; dataframe, обучение и файловый ввод-вывод остаются в adapters.

### Один источник фактов

Добавить версионированный итог запуска, из которого CLI, verifier и веб-панель читают:

- состояние результата и состояние поиска отдельно;
- выбранный рецепт и происхождение гипотезы;
- измеренные метрики и протокол;
- причины остановки и отказов;
- расход времени, памяти и известность LLM usage.

Новый формат — версия 3. Старые артефакты доступны для просмотра; возобновление незавершённого v2-запуска новым исполнителем отклоняется явно. Новые запуски используют отдельные директории.

## 3. Последовательность улучшений

### Этап A. Дать агенту достаточное понимание данных

Подготовить компактный профиль: описание и тип каждого признака, пропуски, число уникальных значений, числовые квантили, частые категории, распределение target, константы и дублирующиеся признаки.

- Обучаемые статистики вычислять по train-части. Target контрольной выборки не использовать.
- Отдельно отражать различия схемы и пропусков train/test.
- Включать профиль и словарь в контекст Qwen вместе с метрикой, контрактом результата и измеренными ошибками.
- Ограничивать размер окончательного сообщения, после добавления рецептов и прошлых результатов.
- Для широких таблиц передавать общий обзор и релевантные подробности; предоставить ограниченный read-only запрос дополнительных сведений по названным колонкам.
- Диагностику распространить на все признаки. В контекст выбирать наиболее существенные сегменты с достаточной поддержкой вместо первых 20 колонок.
- target_error проверять как ссылку на существующее измерение либо явно обозначенную исследовательскую гипотезу.

Приёмка: на синтетической задаче агент получает описание проблемного признака за пределами первых 20 колонок; ограничение контекста не удаляет метрику, бюджет, рецепт родителя и выбранное свидетельство.

### Этап B. Объединить признаки и численный поиск

Снять запрет на сочетание feature transformations и tuning, изменив устройство обучения.

- Каждый trial создаёт новый полный pipeline.
- Преобразования обучаются только на inner-train и применяются к inner-validation.
- После выбора параметров pipeline заново обучается на разрешённой train-части.
- При финальном refit используются сохранённые параметры без повторного поиска.
- Колонки и индексы для group/time-разбиений хранить отдельно от преобразуемых признаков: удаление колонки из модели не должно ломать валидацию.
- Продолжать Optuna study только при совпадении данных, split, структуры pipeline, пространства параметров и метрики.
- Добавить early stopping на внутреннем разбиении; выбранное число итераций сохранять для refit.

Такое размещение преобразований внутри обучения соответствует рекомендациям по предотвращению утечек в scikit-learn (https://scikit-learn.org/1.5/common_pitfalls.html); условные пространства поддерживаются Optuna (https://optuna.readthedocs.io/en/v4.2.1/tutorial/10_key_features/002_configurations.html).

Приёмка: цепочка «Qwen добавила полезный признак → Optuna настроила этот pipeline → refit сохранил признак и параметры» проходит в реальных worker; тесты подтверждают отсутствие доступа преобразований к inner-validation при fit.

### Этап C. Использовать бюджет исследования осмысленно

Заменить жёсткие три гипотезы управлением по оставшимся ресурсам.

- После baseline чередовать содержательную гипотезу Qwen и численный поиск на лучшем полном pipeline.
- Сохранить исследование альтернативной успешной ветки на каждом третьем содержательном шаге.
- Верхний предохранительный лимит Qwen-гипотез — 12; максимум две коррекции на гипотезу. Реальное число ограничивают время, токены и резерв завершения.
- После трёх последовательных гипотез без улучшения переключаться на локальный численный поиск до конца доступного бюджета.
- При недоступности Qwen, исчерпании токенов или неизвестном usage прекращать LLM-вызовы, сохраняя возможность локального поиска.
- Допуск обучения рассчитывать по измерениям соответствующего backend и pipeline, включая преобразования и tuning.
- Smoke проверяет исполнимость и стоимость; его метрика не заменяет полноценную оценку качества.
- Резерв завершения рассчитывать по реальному составу финалистов и измеренной стоимости refit.
- Сохранять готовый улучшенный CSV в контрольных точках, когда его создание укладывается в бюджет. После такой публикации поиск продолжается без обращения к control.

Приёмка: после трёх успешных гипотез поиск способен продолжаться; отказ Qwen не завершает полезную локальную работу; любой timeout сохраняет последний проверенный CSV.

### Этап D. Усилить обучение и финальный отбор

- Начальный портфель оставить CatBoost/LightGBM.
- Расширить настройку числа деревьев, сложности, регуляризации и обработки дисбаланса через единый каталог возможностей.
- Для классификации сохранять вероятности с явным порядком классов, даже если submission требует метки.
- Проверять ансамбли вероятностей двух лучших моделей с фиксированными весами 25/75, 50/50 и 75/25; выбирать по development-validation и замораживать до control.
- Для регрессии аналогично проверять усреднение предсказаний.
- Дополнительно проверять линейную модель как дешёвый самостоятельный кандидат; включать её в основной портфель только после сравнительной приёмки.
- Не добавлять stacking и большой набор новых алгоритмов в первую итерацию: сначала измерить вклад перечисленных изменений.

Приёмка: корректное согласование ID/классов, воспроизводимые ансамбли и отсутствие изменения весов после просмотра control.

### Этап E. Согласовать интерфейс и документацию

Веб-панель должна показывать происхождение эксперимента — Qwen или численный поиск, выбранную ветку, причины отклонения, переход на локальный поиск и качество доступного CSV. Успешный выпуск файла и успешное исследование отображаются отдельно.

Добавить новый этап в план разработки, обновить архитектуру и инструкции. Старые непройденные live-критерии сохранить как исторически незакрытые.

## 4. Проверка качества и альтернатив

Проверять изменения на трёх разных уровнях.

Корректность: существующие тесты плюс сценарии утечек между разбиениями, tuning преобразованного pipeline, переставленного порядка классов, позднего API-отказа, прерывания, resume и восстановления финального CSV. После значимых этапов — make check, релевантные тесты; перед выпуском — полный suite, Linux и распакованный ZIP.

Независимое качество: сравнить пять режимов:

1. Замороженный текущий portfolio + Optuna.
2. Новый pipeline и планировщик без Qwen.
3. Новый гибрид с Qwen.
4. AutoGluon с явным набором CAT/GBM/XGB.
5. FLAML с явным набором разрешённых CPU-моделей.

Для AutoGluon/FLAML сохранить внешний worker и evaluator. В частности, AutoGluon допускает обучение на tuning_data в некоторых конфигурациях, а его лимит времени приблизительный: закрытую оценочную выборку туда передавать нельзя. Контракт AutoGluon (https://auto.gluon.ai/1.3.1/api/autogluon.tabular.TabularPredictor.fit.html).

Использовать две публичные задачи и три существующих локальных benchmark-задачи, seeds 7/42/2026. Для публичных задач создать отдельные локальные benchmark-копии с внешней отложенной частью из размеченного train; исходные публичные материалы для functional gate сохранить без изменений.

Внешние targets недоступны исследованию и финальному выбору. Исходники и конфигурации заморожены на весь сравнительный запуск. После просмотра результатов эта выборка становится исследовательской; повторный итоговый аудит требует нового заранее зафиксированного разбиения.

Общие ceilings первоначального сравнения: 1800 секунд, 4 CPU, 6000 MiB, включая подготовку, API и refit. Для финальной версии отдельно проверить полный конкурсный режим: 3 часа, 8 CPU, 32 GB.

Измерять:

- независимую метрику и парную разницу по seeds;
- долю валидных итоговых CSV;
- время до первого обученного результата;
- число завершённых и улучшивших результат экспериментов;
- wall-clock, пик памяти и LLM usage;
- вклад Qwen относительно того же нового pipeline без Qwen.

Критерий пользы гибрида: положительный средний парный прирост минимум на двух задачах и положительный общий нормированный прирост по пяти задачам, без потери надёжности. Три seed дают описательное сравнение, а не статистическую гарантию. Победа на development-validation не засчитывается как доказательство.

Целевая Qwen: после получения конфигурации — ограниченная проверка транспорта и tool calling, smoke, затем functional gate на обеих публичных задачах. Только после этого — сравнительная серия с Qwen. Старые результаты на другой модели не переносить.

## 5. Условия выпуска и ограничения

- Основная архитектура — управляемый гибрид. AutoGluon и FLAML сначала используются как сравнительные движки; переход на один из них не выполняется автоматически по одному удачному запуску.
- Сохраняются конкурсный интерфейс solution.py, существующие режимы запуска и ограничения ресурсов. Режим qwen получает новый гибридный поиск, optuna использует тот же pipeline без LLM.
- Версии библиотек соответствуют списку организаторов; изменения зависимостей сопровождаются обновлением lock-файла.
- Целевая Qwen пока недоступна. Независимые этапы выполняются без неё, но итоговая live-приёмка остаётся открытой.
- Суточные денежные ограничения не подменяются предположением о стоимости токена: объём live-серии согласуется с известной квотой провайдера.
- Расширение за пределы табличной регрессии и классификации, мультиагентная система и полная перепись проекта в этот план не входят.

Версия готова к выпуску, когда проверены сохранность результата, полный путь на целевой Qwen, переносимость ZIP и независимое качество. Зелёные тесты подтверждают корректность исполнения; прирост качества подтверждается отдельными измерениями.
