# Какой исполнительный контур брать для хакатона

Проверено 19 октября 2026 по официальным документации и исходникам. Это архитектурная оценка, не результат запуска с выданным Qwen API. Ссылки на `main` могут меняться.

**Рекомендация: небольшой Python-контур поверх интерфейса baseline, с устройством памяти и поиском по версиям из AIDE.** Из готового AIDE имеет смысл перенести отдельные структуры и идеи, сохраняя лицензию при копировании кода. OpenCode пригоден для локального сравнительного прогона, но его упаковка в конкурсный runtime добавляет работу без готового решения вопросов ML-валидации и отбора моделей.

## Что действительно даёт AIDE

- В `agent.py` есть три операции: создать независимое решение, исправить сломанное, улучшить выбранное. Выбор обычно жадный по лучшей метрике; это не обязательный MCTS и не команда агентов. Улучшение получает код родителя и сводку журнала. Метрику штатно извлекает LLM из вывода сгенерированной программы; фиксированный внешний оценщик этим не обеспечивается. Промпт предлагает агенту самому посчитать валидацию и записать submission. [Код Agent](https://github.com/WecoAI/aideml/blob/main/aide/agent.py).
- `Node` хранит код, план, родителя, время, ошибку, метрику и вывод. `Journal.generate_summary()` собирает краткие записи только успешных узлов, без кода по умолчанию. Это удобная отправная точка, но отрицательные результаты и падения нужно сохранять в нашей памяти отдельно. Накопление всех успешных записей также требует ограничения размера. [Journal](https://github.com/WecoAI/aideml/blob/main/aide/journal.py).
- Исполнитель уже умеет отдельный процесс, stdout/stderr, traceback и таймаут. Это полезный образец; он не заменяет общий дедлайн задачи и резерв для финального обучения. [Interpreter](https://github.com/WecoAI/aideml/blob/main/aide/interpreter.py).
- Пакет заявляет Python >=3.10, но установка `aideml` забирает весь `requirements.txt`: туда входят не только собственные утилиты, но torch, torchvision, torchtext, transformers, старый закреплённый datasets и множество других библиотек. Python 3.12 формально удовлетворяет ограничению версии самого пакета; совместимость полного дерева зависимостей с образом организаторов этим не доказана. [setup.py](https://github.com/WecoAI/aideml/blob/main/setup.py), [requirements](https://github.com/WecoAI/aideml/blob/main/requirements.txt).
- Лицензия MIT допускает перенос кода с сохранением уведомления. [Лицензия](https://github.com/WecoAI/aideml/blob/main/LICENSE).

**Что потребуется изменить даже в облегчённом форке:** внешний подсчёт метрики, неизменяемые индексы разбиения, журнал неудач, ограничения времени и памяти, проверка и атомарная замена submission, входной интерфейс конкурса. Поэтому брать библиотеку целиком ради готового «агентного цикла» здесь не очевидная экономия.

В прочитанном основном агентом requirements организаторов есть `openai==1.68.2`, `pydantic==2.10.6`, `psutil==6.1.1`, CatBoost, LightGBM, XGBoost и sklearn. Текущий AIDE требует `openai>=1.69.0`: уже этого достаточно, чтобы не считать его установку в неизменном виде совместимой. Собственный контур может опираться на уже разрешённые openai/pydantic/psutil и стандартную библиотеку. [Requirements организаторов](https://drive.google.com/file/d/1qmh2gFibCFfwbAKe6d6FCudv-zzjbnCY/view), [requirements AIDE](https://github.com/WecoAI/aideml/blob/main/requirements.txt).

## Qwen: поддержка endpoint не равна проверенной совместимости

В AIDE произвольное имя модели при заданном `OPENAI_BASE_URL` направляется в OpenAI-compatible backend. Он вызывает Chat Completions, а для обратной связи отправляет `tools` и принудительный `tool_choice`, ожидая ровно один корректный вызов. Значит, нужны реальная поддержка этих параметров выданным сервером и корректная схема ответа; одного совпадения `/v1` недостаточно. [Маршрутизация](https://github.com/WecoAI/aideml/blob/main/aide/backend/__init__.py), [backend](https://github.com/WecoAI/aideml/blob/main/aide/backend/backend_openai.py).

По умолчанию AIDE использует разные OpenAI-модели для code, feedback и report. Все стадии надо направить на разрешённую модель; report можно отключить. Иначе настройка только coding-модели оставит запрещённые обращения. [Конфигурация](https://github.com/WecoAI/aideml/blob/main/aide/utils/config.yaml).

Для нашего контура достаточно одного API-клиента и проверки при старте: обычный ответ, один tool call, usage, предельный ответ, таймаут. Если tool calling нестабилен, один JSON-конверт с локальной проверкой и ограниченным повтором проще, чем перенос провайдерной инфраструктуры. Это предлагаемое решение; endpoint организаторов здесь не тестировался.

## Что действительно даёт OpenCode

Есть неинтерактивный `opencode run`, продолжение сессии, выбор модели и вывод событий JSON. [CLI](https://opencode.ai/docs/cli/). Есть пользовательский provider с baseURL, ключом и `@ai-sdk/openai-compatible` для Chat Completions. [Providers](https://opencode.ai/docs/providers/). Есть автоматическое сжатие сессии и удаление старых выводов инструментов; также настройки отключения обновлений и ограничения списка провайдеров. [Config](https://opencode.ai/docs/config/).

Однако это отдельный runtime: официально доступны установщики и бинарники, а не Python-модуль для импорта из `solution.py`. Поставить бинарник заранее технически возможно, но его допустимость и работа в контейнере конкурса требуют проверки. Утверждать, что OpenCode непременно требует установленного Node.js, неверно: документация предлагает готовый binary. [Установка](https://opencode.ai/docs/).

На момент проверки существуют документации OpenCode 1 и 2 с разными схемами настройки. Следует закреплять конкретную версию, а не собирать конфигурацию из разных руководств. [OpenCode 1](https://opencode.ai/docs/), [модели OpenCode 2](https://dev.opencode.ai/v2/docs/models/).

**Вывод:** готовое сжатие переписки полезно, но не является памятью экспериментов. Даже с OpenCode всё равно нужны отдельный журнал, достоверная метрика, управление ресурсами и сохранение лучшего артефакта. Для единственного Python entrypoint это дополнительный слой.

## Предлагаемый минимальный контур

Это проектное решение, не заявленная возможность стороннего проекта:

1. Контроллер читает контракт задачи и создаёт каталог запуска, дедлайн, профиль данных и стабильный протокол валидации.
2. LLM получает описание, профиль, ограниченную сводку выбранных успешных и неудачных экспериментов, лучшие кандидаты и оставшийся бюджет. Полный журнал доступен через инструмент чтения. Выбирает родителя и гипотезу.
3. Короткая coding-сессия создаёт новую версию Python-кандидата. Агент может писать признаки, обработку и обучение; свобода не ограничивается словарём гиперпараметров. Доступные модели определяются реальным requirements конкурса.
4. Отдельный runner запускает кандидата с лимитом времени. Контроллер получает предсказания и считает метрику; stdout нужен для диагностики, а не как источник итогового числа.
5. Журнал сохраняет гипотезу, parent, код, статус, метрику, время, причину неудачи. Следующая сессия заново строит небольшой контекст из этих фактов. Полные логи остаются на диске и читаются по запросу.
6. Контроллер сохраняет рабочий submission и обновляет его по основному протоколу отбора. После остановки поиска финалисты проходят однократную дополнительную проверку; её результаты не возвращаются в новый цикл улучшений. Общий дедлайн прерывает поиск заранее с запасом для этой проверки и финального обучения.

Разумная первая версия: один агент, последовательные эксперименты, несколько независимых стартов и улучшения лучших ветвей. Нужность параллельных агентов, сложного поиска по дереву или универсального coding harness проверять только после измерения частоты успешных экспериментов и прироста качества на одинаковом бюджете.

Выбор основан на контроле эксперимента в пределах 8 CPU / 32 GB / 3 часов и разрешённых зависимостей, а не на размере команды или сроке разработки. Отдельный evaluator — граница ответственности и воспроизводимости. Если сгенерированный код имеет те же права в том же контейнере, это ещё не security sandbox и не гарантия невозможности прочитать validation targets или изменить файлы оценщика.

## Конкретное решение для реализации

Дальше — предлагаемая архитектура. Её качество на данных конкурса ещё не измерено.

**Один Python-процесс управляет исследованием; Qwen работает короткими сессиями; обучение выполняют дочерние процессы.** В памяти хранится граф воспроизводимых экспериментов. Ветвление означает версии ML-пайплайна, а не одновременный запуск нескольких LLM. Один тяжёлый эксперимент за раз использует доступный CPU-бюджет.

### Вход и границы универсальности

Сохраняем вызов `python solution.py /path/to/task.md` и переменные `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_MODEL`. Реальный baseline читает Markdown и передаёт его модели, запускает Python относительно каталога задачи. Имена выходного файла и столбцов не захардкожены в baseline: их нужно извлечь из материалов конкретной задачи. MCP является устройством baseline, а не обязательным внешним контрактом. [Прочитанный baseline](https://drive.google.com/file/d/17zkL_M4hepUf0AwyZZKSZ6Y3yRPixFjV/view).

Создаём `TaskSpec`: пути, target, ID, тип задачи, метрика и направление, labels/probabilities, порядок классов, формат submission, признаки времени/групп. Qwen интерпретирует условие; Python сверяет вывод с train/test, словарём и образцом. Противоречия возвращаются на исправление. Первое покрытие — табличная регрессия, бинарная и многоклассовая классификация, включая числовые, категориальные, временные и текстовые признаки без предобученных моделей. ТЗ не доказывает, что private ограничен этим набором; абсолютную универсальность не заявляем.

### Что именно может менять агент

Каждая версия содержит `candidate.py`, конфигурацию и ссылку на родителя. Контракт кандидата — создать обучаемый объект с `fit`, `predict` и при необходимости `predict_proba`; адаптер позволяет использовать и обычные sklearn-пайплайны, и более сложную процедуру обучения. Harness подаёт одинаковые разбиения, проверяет размер/порядок предсказаний и считает внешнюю метрику. Внутреннюю валидацию для early stopping кандидат получает отдельно от контрольной выборки финалистов.

Qwen может менять преобразования признаков, обучение, семейство модели, loss и ограниченный поиск параметров. Для нестандартного подхода он пишет новый адаптер. Разбиение, оценщик и публикация результата остаются ответственностью harness. Любая смена основного разбиения создаёт новый протокол и требует переоценки сравниваемых кандидатов. При переобучении все обучаемые преобразования обучаются заново только на доступной обучающей части: особенно target encoding, заполнение пропусков и отбор признаков.

Предоставляем готовые рабочие примеры CatBoost и LightGBM: это отправные точки, а не закрытый список действий. AutoGluon — самостоятельный сильный кандидат и обязательный ориентир для локального сравнения. При его использовании явно задаём разрешённые модели, например `GBM` и `CAT`, CPU-ресурсы и бюджет; не включаем произвольный preset с непроверенным составом моделей. В разрешённой версии 1.3.1 есть `hyperparameters`, `num_cpus`, `num_gpus`, `time_limit`; последний ограничивает время приблизительно, поэтому внешний таймаут остаётся необходимым. [Документация версии 1.3.1](https://auto.gluon.ai/1.3.1/api/autogluon.tabular.TabularPredictor.fit.html).

### Один исследовательский шаг

1. Профиль данных и диагностика ошибок указывают на проблему. Для классификации сохраняем support/precision/recall/F1 по классам и матрицу ошибок; для регрессии — ошибки по диапазонам и достаточно крупным сегментам. Это наблюдения, а не доказанные причины ошибок.
2. Qwen выбирает родителя, одну проверяемую гипотезу и бюджет. Пример: редкие классы часто пропускаются → проверить умеренные веса классов при прежних признаках и разбиении.
3. Короткая рабочая сессия читает нужные участки кода и пишет новую версию. Сначала проверка синтаксиса и маленький пробный запуск, затем полноценный эксперимент. Маленькая выборка проверяет работоспособность; её метрика не сравнивается с полноценной валидацией и не должна исключать редкие классы по случайности.
4. Runner сохраняет предсказания, модель, время, пик памяти и полный лог. Harness вычисляет метрику. При ошибке допускается ограниченное число исправлений, затем ветка получает статус failed.
5. Новая версия может стать лидером, остаться альтернативой для ансамбля или быть отвергнута. Неудачи сохраняются с условиями эксперимента: «не помогло здесь» не означает глобальный запрет гипотезы.

Внутри такого шага Optuna может проверить числовые гиперпараметры без отдельного LLM-вызова на каждый trial. Qwen определяет содержательное направление поиска и ограничения; алгоритм выполняет рутинный перебор. Полноценные датасеты, ранняя остановка и пилотные запуски имеют разные уровни проверки и явно помечаются в журнале.

### Память, инструменты и бюджеты

Для одного последовательного контроллера достаточно JSONL-журнала и каталогов артефактов. Запись: ID/parent, гипотеза, хеш кода и конфигурации, версия данных/разбиения, статус, метрика, время, ресурсные затраты, пути к модели/предсказаниям/логам. Отдельно сохраняется краткая интерпретация Qwen. Числа и статусы пишет контроллер.

На новую сессию подаются TaskSpec, профиль, выбранный родитель, ограниченная сводка лидеров и релевантных неудач, текущая диагностика и оставшиеся ресурсы. Полный журнал не вставляется. Достаточны инструменты чтения файла по диапазону, записи/точечной правки кандидата, запуска эксперимента и чтения артефактов/журнала. Повторный доступ к неизменившимся фактам не требует повторного анализа LLM. Внутри сессии остаётся локальная история исправлений; новая гипотеза начинает новый контекст. Контекстное окно, совокупный token usage и таймер задачи контролируются раздельно.

Запуск обучения не требует постоянных LLM-опросов статуса. Контроллер ждёт процесс, пишет его вывод на диск, прерывает группу процессов по дедлайну и ограничивает число потоков библиотек. `psutil` позволяет наблюдать дерево процессов и RSS; мониторинг памяти сам по себе не является жёстким OS-лимитом. Применимость более сильной изоляции зависит от прав внутри контейнера организаторов.

### Отбор и завершение

Сразу после первой рабочей модели сохраняем её тестовые предсказания; обучение на полном train для первого корректного submission не обязательно. Затем улучшения обновляют рабочий файл через проверку и атомарную замену. Рабочий файл существует и при недоступности Qwen после первого результата.

Схема разбиения зависит от условия и структуры данных: стратификация, группы или время. Если объём данных позволяет, выделяем контрольную часть, которую поиск не использует. После остановки исследования фиксируем небольшое число финалистов и однократно проверяем их на ней; результаты не возвращаем в новый поиск. Такая проверка снижает адаптацию к основной валидации, но не гарантирует качество на private. Для маленьких данных и редких классов размер/схема проверки требуют другой стратегии, а не обязательного универсального 80/10/10.

Простой ансамбль проверяется только для сопоставимых предсказаний с одинаковыми ID, классами и разбиениями. Для RMSE смешиваем числовые прогнозы; для классификации — вероятности с согласованным порядком классов, после чего считаем целевую метрику. Усреднение само по себе не гарантирует улучшения. Подбор весов выполняем до контрольной проверки финалистов.

Остановку поиска определяем по оставшемуся времени и измеренной стоимости проверки, refit и predict с запасом. Если резерв недостаточен, оставляем уже готовый лучший результат. Финальный refit — отдельный запуск с тем же препроцессингом; он не должен уничтожить предыдущую рабочую модель или submission.

### Модули и критерий готовности

| Модуль | Ответственность |
|---|---|
| `solution.py` | Входной контракт и запуск |
| `task.py` | TaskSpec, профиль, метрики и протокол разбиения |
| `research.py` | Выбор гипотезы, сбор контекста, API/tool loop |
| `experiments.py` | Версии кандидатов, журнал и артефакты |
| `runner.py` | Процессы, таймауты, ресурсы, результаты |
| `selection.py` | Сравнение предсказаний, финалисты, refit и submission |
| `templates/` | Стартовые модели и примеры адаптеров |

Порядок реализации: (1) вход → рабочая модель → проверенный submission, (2) одна гипотеза Qwen → исполнение → объективная оценка, (3) несколько сессий с восстановлением состояния и обработкой ошибок, (4) перенос на незнакомые данные и сравнение качества. Эти этапы проверяют отдельные риски и не являются оценкой сроков.

Сравниваем при одинаковых ресурсах три режима: сильный фиксированный ML-пайплайн, тот же пайплайн с обычным подбором параметров, полный LLM-цикл. Используем несколько задач, не использованных при разработке промптов; внешние наборы — только для проверки общего агента, не для обучения конкурсных предсказаний. Фиксируем валидность submission, качество, длительность, расход LLM и долю успешных экспериментов. Наиболее важный результат — воспроизводимый прирост от исследовательского цикла с учётом потерянного на него времени обучения.

Первый интеграционный прогон должен доказать: Qwen понял задачу, предложил и исполнил несколько разных гипотез, ошибка одного кандидата не остановила запуск, новая сессия помнит прошлые неудачи, а принудительное завершение оставляет корректный CSV. Рост метрики пока является проверяемой целью, а не установленным фактом.
